# UI 코드 검사 결과

이 문서는 리팩터링 이전의 검사 스냅샷이다. 이후 UI 구조와 갱신 방식은 정리했으며 현재 구성과 검증 결과는 [UI_REFACTOR.md](UI_REFACTOR.md)를 참고한다. 아래 네 가지 재현 오류는 사용자 지시에 따라 보류했다.

검사일: 2026-10-31. 대상은 이 채팅에서 추가한 전투·보상 UI, 보상 처리, 공용 전투 코드의 두 수정 구간이다. 개발 기획과 이후 사용자 정정사항을 기준으로 검사했다. 이번 검사는 수정 작업이 아니며, 게임 코드·씬·프리팹은 변경하지 않았다. 재현 테스트의 런 상태는 Play 종료로 되돌렸다.

## 결론

현재 기본 카드로 전투와 보상을 확인하는 용도로는 동작하지만, 그대로 팀 통합을 마친 코드로 보기는 어렵다. 우선 처리할 문제는 손패 밖 카드 갱신 예외와 전투 종료 이벤트 완료 전 다음 전투 진입이다. 구조상으로는 UI 참조 캐시와 변경 시점 기반 갱신이 필요하다. 성능 병목이 발생했다는 주장과, 현재 코드에 불필요한 반복 작업이 있다는 판단은 구분한다.

## 구성과 효율성

### 변경 시점 기반 갱신으로 전환 권장 — P2

- `BattleScreenUI`는 4개 partial 파일 합계 1,600줄의 단일 클래스다. 파일을 나눴지만 전투 연출, 선택 대기, 레이아웃 생성, 목록, 보상, 문자열, 그림 대체, 색상 복원이 같은 상태를 공유한다.
- `LateUpdate`에서 변화가 없어도 `RefreshHandLayout`을 호출한다. 매번 `GetComponent`, LINQ `Where().ToList()`, 손패 RectTransform 설정을 반복한다.
- 보상에서는 매 프레임 배경의 모든 Graphic을 순회해 색을 다시 지정한다. 전투와 보상 갱신 경로를 분리하면 상태 진입·일부 표시 변경 시에만 처리할 수 있다.
- `RefreshAll`은 체력 변화·에너지 변화·선택 변경 등에서 보드, 모든 카드, 모든 적을 다시 읽는다. 카드마다 `Transform.Find`, `GetComponent`로 자식을 반복 탐색한다.
- 카드 목록은 열 때마다 모든 카드를 새로 생성하고 닫아도 보관하다가 다음 열기 때 파괴한다. 20장에는 당장 가상 스크롤이 필요하지 않지만, 재사용과 필요한 영역만 갱신하는 구조가 낫다.

측정 참고: 에디터에서 손패 6장 상태의 정렬 함수를 6,000회 호출한 총 시간은 약 30.36ms, 관리 힙 사용량의 순증가는 약 1.53MB였다. 리플렉션과 에디터 환경이 포함된 참고 측정으로 실제 프레임 시간이나 전체 할당량은 아니다. 해당 런타임의 `GC.GetAllocatedBytesForCurrentThread`는 64KB 제어 배열을 만들어도 0을 반환했으므로 정확한 할당량 근거로 사용하지 않았다. 현재 6장 화면이 느리다고 단정하지 않지만, 지속적인 목록 생성과 반복 탐색은 코드상 확인된다.

권장 분리 수준은 `CardView`, `EnemyView`, 수치 표시, 카드 목록, 보상 화면 정도다. 각 뷰가 Image/Text 참조를 직렬화해 보관하고, 카드 추가·제거·선택 변경에만 손패 정렬을 수행하면 된다. 새 프레임워크나 모든 화면의 풀링부터 도입할 필요는 없다. 레이아웃 제작용 코드는 에디터 쪽으로 모으고 런타임 뷰와 분리하는 것이 좋다.

## 이전 구현의 잔여물

실제 프리팹과 씬에서 삭제 요청했던 `ConfirmLeave`, `rewardSkipButton`, `modalPrevious`, `modalNext`는 발견되지 않았다. 경고창·두고 가기·페이지 넘김이 화면에 남아 있는 상태는 아니다. 다만 아래 정리 대상은 남아 있다.

- `BattleScreenUI.cs`의 미사용 `EnemyBase`, `Pickable`, `IntentSummary`, `EffectName`.
- `log` 참조와 `UnusedLog` 오브젝트. `UnusedHud`는 이름과 달리 팝업 폰트 공급에 사용되므로 폰트 참조를 먼저 옮겨야 제거할 수 있다.
- 승리 시에는 사용하지 않는 결과창의 `nextBattleButton`과 항상 패배 분기로만 도달하는 `won ? ...` 식.
- UI 문자열의 `leaveCard`, `leaveRewardsConfirm`, `previous`, `next`.
- 보상 처리의 현재 미사용 `SkipRewardCard`, `HasRemaining`. 공개 API이므로 추후 호출 계획을 확인한 뒤 정리한다.
- 에디터 생성기에 남은 단계별 마이그레이션 함수들. 재구성 함수는 기존 프리팹의 수동 그림·설명 설정을 덮어쓸 수 있고, 초기 덱 20장은 별도 마이그레이션에만 있어 재생성 경로와 최종 상태가 일치하지 않는다.
- `Docs/BATTLE_UI.md`에 남은 ‘목록·후보·확인창’ 표현과 ‘전투 코드는 순간이동만 수정’이라는 오래된 설명. 실제로는 카드 종료 시 승리 판정도 변경했다.
- `Captures/`의 이전 버전 검증 이미지. 런타임 의존성이 없으므로 전부 커밋할 필요가 없다.

`TempBattleUI`, 기존 BattleUI 프리팹, SampleScene은 잔여물로 보고 삭제하면 안 된다. 기존 공용 씬에서 계속 사용하며 팀원들이 작업하는 기준이기도 하다.

## 향후 기획 기능과의 연결

1. **다중 적:** 적 영역이 여러 적에게 분배돼도 사기 막대는 고정 `342` 폭이다. 적 수가 늘면 자기 영역을 넘는다. `RefreshEnemy`는 실제 Bar 폭 기준으로 계산해야 한다. NDM의 단일 적 전제에서는 현재 필수 기능 결함으로 분류하지 않았다.
2. **신규·복합 효과:** 사기 증가 예고는 현재 타일의 직접적인 `GainMoraleEffect`만 합산한다. 효과 설명은 구체 클래스별 switch, 폭탄 키워드 설명은 번역된 설명문에서 단어를 찾는 방식이다. 복합 효과나 새 적 패턴이 들어오면 미리보기/설명 계약을 추가해야 한다.
3. **잠금·해금·질주:** 실제 처리는 기존 전투 코드의 TODO다. 현재 UI의 잠금 회색 표시를 전체 기능 구현으로 간주하면 안 된다. 이동 진행 큐·비용·재사용 상태를 카드 담당자가 제공한 뒤 표시를 연결해야 한다. UI에서 별도 규칙을 복제하면 안 된다.
4. **장애물 대상:** UI는 장애물 선택 후보를 표시할 수 있지만, 기존 BattleManager의 Unit 대상 후보에는 적만 들어간다. 장애물을 직접 선택하는 카드가 추가되면 전투 담당자가 후보를 확장해야 한다. 이번 UI가 새로 만든 제한은 아니다.
5. **배포 폰트:** 프로젝트에 한국어 폰트를 포함하지 않고 OS 설치 폰트를 찾는다. 현재 Windows 에디터에서는 동작하지만 다른 환경의 한글 표시는 보장되지 않는다. 배포 대상에 맞는 폰트 에셋이 필요하다.
6. **진행 경로:** 다음 전투는 현재 매니저의 동일 적/설정으로 다시 시작한다. 지도·막 진행·보스·엘리트 보상·유물은 이번 요청에서 제외한 범위다. 보상 버튼이 최종 게임 진행기를 대신하도록 확장하면 안 된다.
7. **빌드 통합:** 현재 활성 빌드 씬은 SampleScene 하나다. 지금 빌드하면 새 UI 테스트 씬이 시작되지 않는다. 별도 씬은 충돌을 줄이려는 의도된 선택이지만, 배포 전 통합은 별도 작업으로 남아 있다. 이번 검사에서 실제 플레이어 빌드는 실행하지 않았다.

## 협업·파일 충돌 검사

### 이 UI 작업의 병합 범위

- 기존 공용 파일의 필수 변경은 `Assets/Scripts/Battle/BattleContext.cs`의 두 기능: 순간이동 에너지 1 소비/부족 시 차단, 카드 효과와 반응 완료 후 적 사기 0 판정이다. 전투 흐름 담당자가 같은 파일을 수정 중이면 이 두 구간을 협의해야 한다.
- 실제 보상 지급은 신규 `Assets/Scripts/Battle/BattleContext.Rewards.cs`에 추가했다. 기존 메서드의 이름·인자는 바꾸지 않았다. 팀원이 별도 보상을 구현 중이면 추가 API와 책임 범위를 공유해야 한다.
- 새 UI, 프리팹, 아트, UI 문자열, 전용 씬은 추가 파일이다. 새 파일이라 원래 파일과의 텍스트 충돌은 적지만 `.meta`와 함께 전달해야 한다.
- SampleScene, 기존 BattleUI 프리팹, BattleManager, 카드·효과·적·유물 담당 소스의 변경은 확인되지 않았다.

### UI 커밋에 섞지 않을 변경

작업 시작 시점부터 DOTween/URP 설정, Packages, ProjectSettings, `.vscode`가 변경 또는 미추적 상태였다. 무조건 `git add .`로 묶으면 UI와 관계없는 변경이 섞인다. 검사에서 실제 내용 차이가 확인된 것은 MCP 패키지 의존성 추가와 QualitySettings의 버전/직렬화 항목 변화다. 다른 표시 파일 일부는 줄바꿈을 무시하면 내용 차이가 없다. 이 검사에서 임의로 되돌리지 않았다.

필수 커밋 목록은 `BattleContext.cs`의 두 수정 구간, 신규 Rewards 파일, 신규 UI/Editor 파일, BattleScreen 프리팹, BattleUIScreen 씬, Art/UI, Resources/UI와 각 `.meta`다. Docs와 검증 이미지는 필요에 따라 별도로 묶는다. Packages/ProjectSettings 변경은 별도 의도와 팀 합의가 없는 한 UI 커밋에 포함하지 않는 편이 좋다.

## 검증 결과와 한계

이번 검사에서 직접 확인한 사항:

- 코드 컴파일 오류 없음. 기존 DOTween PluginImporter 버전 경고는 남아 있다.
- 새 에셋·폴더 26개 대상 `.meta` 누락 없음. Assets 전체의 중복 GUID 없음.
- 새 프리팹의 누락 스크립트 0개. 주요 보드·카드·적·목록·보상·재질 참조 존재.
- 취소된 확인창/건너뛰기/페이지 버튼의 실제 프리팹 잔존 없음.
- 손패 밖 카드 갱신 예외 재현.
- 언어 변경 후 고정 덱 버튼 한국어 잔존 재현. 언어는 검사 후 원래 값으로 복원.
- 종료 이벤트 완료 전 다음 전투 진입 재현. 이벤트 대기를 해제하고 테스트를 종료.
- 선택 대기 상태에서 UI 제거 후 입력 대기 잔존 재현. Play 종료로 씬 복원.
- 골드 10의 중복 수령 차단, HP 49에서 회복 후 50 상한, 카드 선택 시 덱 1장 증가 및 두 번째 선택 차단, 후보 재추첨 방지, 보상 닫기 상태 유지 통과.
- 공용 씬/프리팹 및 타 담당 소스 변경 여부와 빌드 씬 설정 검사.

이 문서는 특정 기기의 프레임 성능 보증, 모든 신규 효과 조합의 검증, 실제 플레이어 빌드 성공, 아직 받지 않은 팀원 브랜치와의 충돌 없음까지 보장하지 않는다. 특히 팀원 쪽 변경 내용은 현재 체크아웃에 없어 실제 병합 결과를 시험할 수 없다.

## 권장 작업 순서

1. 손패 밖 카드 갱신 예외와 선택 대기 취소 처리.
2. 전투 종료 정산 완료와 보상/다음 전투 진입 시점 합의.

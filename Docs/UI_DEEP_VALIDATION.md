# 전투 UI 추가 검증

후속 상태: 아래 검증은 수정 전 기록이다. 표시 결함·배경 복원·보상 정책 분리·갱신 비용의 후속 수정과 재검증은 `UI_REFACTOR.md`의 "추가 수정"에 정리했다. 손패 문제는 보존 기능을 추가하지 않고 전투 종료 시 버리지 않는 방식으로 해결했다. 기존 보류 네 오류와 빌드 문제는 남아 있다.

2026-10-31. UI 리팩터링 이후 코드 경로 검토와 Unity 실행 검사를 진행했다. 이번에는 게임 코드·프리팹·씬을 수정하지 않았다. 빌드가 자동 저장한 설정의 추가 변경은 제거했고, 작업 전부터 있던 의미 있는 변경은 유지했다. 이전에 보류한 네 오류는 수정 대상에서 제외했다.

## 결론

현재의 표시 컴포넌트 분리, 상태 변경 알림에 따른 갱신, 카드 뷰 재사용은 턴제 덱빌딩 게임에 적합하다. 전투 상태와 표시가 분리되어 있고, 매 프레임 전체 카드를 다시 그리지 않는 방향도 유지해야 한다.

그러나 추가로 손볼 부분이 없다는 판정은 내릴 수 없다. 기본 카드만 반복 사용하는 검사에서는 드러나지 않는 정보 갱신·숨은 정보·보존 카드 문제를 확인했다. 앞으로 기능을 붙이기 전에 보완할 책임 경계도 남아 있다. 이를 해결하지 않은 채 구조 개선이 끝났다고 취급하면 안 된다.

## 이번에 확인한 결함

모두 별도로 적은 기존 보류 네 항목과 구분한다. P2는 일반 플레이 또는 예정된 카드 변형에서 잘못된 표시가 발생하는 수준이다.

### 1. P2 — 보존 카드가 있으면 보상 배경 손패가 누락된다

위치: `BattleScreenUI.Rewards.cs:64–80`, `BattleScreenUI.cs:66–69`.

손패 6장 중 한 장에 공개 API `AddKeyword(Retain)`을 적용했다. 적의 타일 효과를 제거하고 사기를 0으로 만든 뒤 UI 턴 종료 버튼을 실행했다. 승리 시 실제 손패는 보존 카드 1장, 저장된 직전 손패는 6장이지만 배경에 표시되는 카드는 1장이었다.

`cards.Count == 0`일 때만 직전 손패를 복원하기 때문이다. 일반 카드 사용 승리와 턴 종료 승리를 구분하고, 턴 종료 전 시각적 손패 전체를 독립적으로 보존해야 한다. 현재처럼 배경용 카드를 실제 손패 표시용 `cards` 사전에 넣는 방식도 분리하는 편이 안전하다. 스냅샷은 인스턴스 참조 목록이므로 종료 효과가 원본을 바꿀 경우 어느 시점의 모습을 유지할지도 명시해야 한다.

### 2. P2 — 표시 중인 카드의 변경이 상세 정보에 반영되지 않는다

위치: `BattleScreenUI.cs:323`, `BattleScreenUI.Layout.cs:193`.

손패 카드 상세를 연 상태에서 `ctx.AddKeyword(card, Retain)`을 실행했다. 모델에는 키워드가 추가되지만 `detailDescription.text`는 변경 전 문자열 그대로였다. `CardChanged`는 손패 작은 그림만 갱신하며 상세 패널을 갱신하지 않는다.

현재 정보의 대상과 카드 인스턴스를 연결하고, 그 카드가 변경되면 현재 호버 우선순위에 맞춰 상세 내용도 갱신해야 한다. 선택 카드 설명뿐 아니라 브라우저·보상 상세에도 동일한 규칙을 적용해야 한다. 손패 밖 카드에서 예외가 발생하는 기존 보류 항목과는 별개다.

### 3. P2 — 뽑을 더미에서 같은 종류의 변형 카드 순서가 노출된다

위치: `BattleScreenUI.Browser.cs:14`.

같은 `CardData.id`를 공유하되 한 장에만 `Free`가 붙은 두 인스턴스로 검사했다. 숨김 옵션을 켜도 입력이 `[A,B]`이면 표시가 `[A,B]`, 입력을 뒤집으면 `[B,A]`로 바뀌었다. 안정 정렬인 `OrderBy(id)`가 같은 ID 사이의 원래 순서를 유지하기 때문이다. 사용자는 상세 정보로 변형본을 구분할 수 있다.

동일한 기본 카드만 있을 때는 차이가 드러나지 않지만, 카드별 이동·키워드를 바꿀 수 있는 현재 모델에서는 숨은 정보를 보장하지 못한다. 표시 가능한 인스턴스 특성까지 포함한 별도 정렬 키로 정렬해야 한다. 이를 위해 게임 RNG를 소비하거나 실제 더미를 정렬해서는 안 된다.

### 4. P2 — 목록을 닫을 때 숨겨진 카드의 호버 소유권이 남는다

위치: `BattleScreenUI.Layout.cs:123`, `BattleScreenUI.Layout.cs:81`, `BattleCardView.cs:72–73`, `BattleScreenPointer.cs:35`.

브라우저 카드에 포인터 Enter를 전달한 뒤 `Back`으로 목록을 닫았다. 목록이 비활성화된 뒤와 다음 검사 호출에서도 `hoveredInfoOwner`와 카드 상세가 남았다. 닫기 버튼도 단순히 목록을 비활성화한다. `OnDisable`에서는 호버 해제가 이루어지지 않는다.

검사는 포인터 릴레이를 직접 호출한 구성 요소 검사다. 실제 마우스를 모든 경로로 조작한 입력 자동화 검사는 아니다. 다만 닫기 경로가 포인터 Exit 전달에 의존하며 자체적으로 소유권을 해제하지 않는 점은 코드에서도 확인된다. 목록 닫기·보상 화면 전환·뷰 비활성화 때 자신이 보유한 호버를 명시적으로 반납해야 한다. 다른 정보의 호버까지 지우지 않도록 소유자 확인도 유지해야 한다.

### 5. 확장 시 결함 — 배경 효과 종료가 원래 상태를 복원하지 않는다

위치: `BattleBackdropView.cs:16–55`.

임시 버튼에 CanvasGroup 알파 0.7, 입력 두 플래그 false, 렌더 색 `(0.8,0.7,0.6,0.9)`를 설정하고 Enter/Exit를 실행했다. 결과는 알파 1, 입력 두 플래그 true, 렌더 색 흰색이었다. 버튼 색을 흰색으로 만든 뒤 복원 색을 저장하며, CanvasGroup의 이전 상태는 저장하지 않는다.

현재 화면에서 알파 1·입력 가능을 전제로 한 일반 경로는 동작한다. 그러나 다른 페이드·입력 잠금과 조합하면 원래 의도를 덮어쓴다. 효과 적용 전에 기존 상태를 저장하고 종료 때 정확히 복구해야 한다. 새로 만든 그룹과 이미 있던 그룹도 구분해야 한다. 보상 배경 때문에 투명도가 바뀌지 않아야 한다는 요구에도 이 방식이 더 잘 맞는다.

## 연산·수명·성능 판단

현재 유지할 선택:

- 턴제이고 손패 수가 작으므로 알림 단위의 작은 갱신과 최대 사용량까지의 풀은 적절하다. 전체 UI 이벤트 버스나 모든 데이터를 복제하는 체계를 추가할 근거는 없다.
- 덱 조회는 원본 순서를 바꾸지 않는 복사본이다. UI 조회/호버/정렬 코드에 게임 RNG 호출이 없다. 보상 생성의 RNG는 Context API에서 사용한다.
- 목록 오브젝트를 매번 파괴하지 않고, 손패 반환 시 바인딩을 해제한다. 재사용 검사에서 카드와 버튼의 연결이 어긋나지 않았다.
- 보드/적은 전투 시작 때 다시 만들지만, 작은 9–25칸 보드를 전환 시 한 번 생성하는 것까지 무조건 풀링할 필요는 없다.

남은 불필요한 작업:

- `BattleScreenPointer.Update`가 Hold 기능이 없는 타일·카드·버튼에도 존재한다. 매 프레임 대체로 즉시 반환하지만 목록을 열면 슬롯 수만큼 호출 수가 늘어난다. 길게 누르기가 필요한 에너지 버튼만 별도 동작을 갖거나 누르는 동안만 갱신하도록 줄일 수 있다. 심각한 프레임 저하를 측정한 것은 아니다.
- `RefreshScreenHud`는 HP/에너지/턴/더미 수를 모두 조합한다. 드로우 애니메이션마다 전체 문자열을 만들 필요는 없다. 더미 수와 자원 표시를 나누고 값이 달라졌을 때만 조합하는 것이 다음 단계다. 턴 시작을 한꺼번에 처리해 드로우 애니메이션 중 수치를 멈추는 것은 피한다.
- 호버마다 설명과 예고 문자열을 새로 조합하는 것은 작은 수에서는 허용 가능하다. 캐시를 추가한다면 먼저 카드 변경·언어·상태 변경의 무효화 규칙을 완성해야 한다. 이번 상세 갱신 결함을 그대로 둔 채 캐시부터 늘리면 안 된다.
- Popup은 생성/파괴 방식이다. 연쇄 효과에서 문제가 되는지는 실제 동시 개수와 프로파일로 판단한 뒤 풀링한다. 덱 수백 장의 가상 목록과 Canvas 분할도 같은 기준이다. 현재 검사만으로 GC 할당 0 또는 모든 기기의 성능을 보증할 수 없다.

검사에는 실제 Context API 호출과 구성 요소 메서드 직접 호출이 함께 사용되었다. 모든 검사가 실제 마우스 입력의 자동 플레이인 것은 아니다. 트윈을 강제 완료한 반복 검사는 연결과 종료 상태를 확인하며 실제 연출 중 타이밍/대상 기기의 프레임 시간을 대신하지 않는다.

## Windows 빌드 결과와 검증 한계

BattleUIScreen을 명시적으로 지정해 Windows64 Development 빌드를 시도했다. 저장된 빌드 씬 목록을 변경하지 않았다. 약 98초 후 실패했다.

오류: `ExecutionEngineException: String conversion error: Illegal byte sequence encounted in the input.`

실패 스택은 Input System의 `LinkFileGenerator.GenerateAdditionalLinkXmlFile` → `Assembly.GetName` → `RuntimeAssembly.get_CodeBase`다. UI C# 컴파일 오류로 단정할 근거는 없으며, 경로 인코딩/어셈블리 메타데이터 변환 문제 가능성이 있다. 정확한 원인은 별도 격리 검사가 필요하다. 폴더를 옮기거나 패키지를 바꾸는 작업은 이번 UI 검증에서 하지 않았다.

실행 파일 실행 검증과 실제 플레이어 프로파일링은 완료하지 못했다. 빌드 성공, 다른 PC 한글 표시, 해상도 전체 범위의 입력/레이아웃을 통과했다고 표시하지 않는다. 기본 활성 빌드 씬은 여전히 SampleScene이므로 최종 배포 통합도 남아 있다.

## 협업 검증

- 공용 원본 소스의 UI 작업 변경은 기존 `BattleContext.cs` 6줄 추가/2줄 삭제: 순간이동 비용, 카드 전체 처리 후 승리 판단이다. 기존 공개 시그니처 변경은 없다. 이 부분은 전투 흐름 담당자의 동시 수정과 충돌할 수 있다.
- 신규 Rewards partial은 파일 충돌을 줄이지만, 팀원이 작성할 보상/진행 코드와 의미상 중복될 수 있다. 공개 API의 소유자와 보상 정책 책임을 합의해야 한다.
- UI 내부에서는 표시별 컴포넌트가 책임을 가지므로 무조건 루트 조정자에 코드를 추가하지 않아도 된다. 다만 프리팹 한 파일에 아트·배치가 모이므로 두 사람이 동시에 배치를 수정하면 새 파일 여부와 무관하게 충돌한다. Prefab Mode에서 아트 교체 담당을 정하고 수정 범위를 공유하는 것이 좋다.
- 신규 에셋은 아직 미추적 상태다. 전달 시 코드만 보내면 안 되고 프리팹·씬·아트·UI 문자열·재질·meta를 함께 포함해야 한다. 검증 캡처와 기존 Packages/ProjectSettings 변경을 한꺼번에 섞지 않는다.
- 빌드가 자동으로 직렬화한 추가 URP/플레이어/서비스 설정은 이번 검사 뒤 원복했다. 이전부터 존재하던 Packages/QualitySettings 등의 의미 있는 차이는 유지했다.

## 의도적으로 보류한 네 항목

손패 밖 CardChanged 예외, 이전 BattleEnd 완료 전 다음 전투 진입, UI 파괴 시 선택 대기 취소 누락, 언어 변경 후 고정 문구 미갱신. 사용자 요청대로 수정하지 않았다. 이 문서의 추가 발견을 이 네 항목의 해결로 간주하지 않는다.

검사 종료 기준은 현재 구현의 주요 변경 알림·선택/호버/목록·보상 경로를 검토하고, 카드 변형·반복 수명·보드 크기·직렬화/협업·빌드 경계를 확인하는 것으로 잡았다. 새로운 기능과 배포 환경까지 무한히 문제가 없다는 보증은 아니다. 우선순위는 위 표시 결함과 수명 복원 → 보상 정책/예측 데이터 계약 → 측정에 근거한 추가 최적화다.
